## Hallazgos

### 1. CRÍTICO — Falta el campo "Horario de trabajo / visita" en el modal de detalle

El mockup (`renderTicketModalBody`, línea ~699) tiene DOS campos separados debajo de Dirección:
- **"Fecha y hora de servicio"** (`mFechaAgendada`) — con el botón Agendar/Reagendar al lado
- **"Horario de trabajo / visita"** (`mHorario`) — un campo propio, debajo

La implementación real (`TicketDetailModal.tsx`) solo tiene el primero. El segundo no existe en
ningún lado del componente (confirmado: cero menciones de "horario" en todo `atlanticerp-frontend/src`).

Lo interesante es que el propio backend ya documenta esto como una brecha conocida, no resuelta —
`TicketService::detail()` (línea ~156-158):
```php
// "Horario de trabajo/visita" del mockup no tiene columna propia en el esquema de
// Batch 1 — se deriva de scheduled_at/scheduled_ends_at en el frontend.
```
Es decir, el backend expone `scheduled_at` y `scheduled_ends_at` (ambos ya vienen en el payload de
`GET /tickets/{id}`) esperando que el frontend arme el campo "Horario" combinando los dos — pero
`TicketDetailModal.tsx` nunca lo hace, y `TicketScheduleModal.tsx` (REQ-226) tampoco captura una
hora de fin al agendar (`scheduled_ends_at` queda siempre `null` en la práctica hoy). El campo no
aparece ni siquiera como "—".

**Impacto:** el técnico/Aaron no tiene forma de ver o comunicar un rango horario de visita
(solo hora de inicio vía "Fecha y hora de servicio"), que es justamente el dato que el mockup
separa a propósito.

### 2. Moderado — "Contacto" solo muestra nombre, el mockup muestra nombre + teléfono

Mockup: `d.contactoNombre + ' · ' + d.contactoTel` (ej. "Contacto Torre Business Park · 6000-0000").
Implementación real: `DetailField` para "Contacto" solo renderiza `ticket.contacto` (el nombre).

El dato de teléfono SÍ se captura y persiste — `StoreTicketRequest`/`TicketService` guardan
`telefono` en la tabla `tickets` (confirmado: `'telefono' => $data['telefono'] ?? null` en
`store()`) — pero `TicketService::detail()` (el método que arma el payload de
`GET /tickets/{id}`) nunca lo incluye en el array de respuesta. No es un problema de frontend: el
dato ni siquiera llega a la API de detalle, así que no hay forma de mostrarlo sin tocar el backend
primero.

### 3. Menor — "Requerimientos especiales" es texto libre en la app real, checklist estructurado en el mockup

El mockup no usa un textarea: `REQ_LABELS` (línea ~861) define un catálogo fijo de 18 ítems de
seguridad/logística (Casco de seguridad, Botas de seguridad, Arnés de seguridad, Permiso de
trabajo en altura, Corte de energía previo (LOTO), Requiere 2 técnicos, etc. — ver lista completa
en el archivo), renderizados como chips seleccionables + "+ Agregar otro" para texto libre
adicional. La implementación real es un único `<textarea>` de texto libre, sin esos 18 ítems
predefinidos.

Marco esto como **menor y no bloqueante** (a diferencia de los hallazgos 1 y 2) porque a diferencia
de un campo ausente, acá sí hay un campo funcionalmente equivalente (el usuario puede escribir
cualquiera de esos requisitos como texto) — pero es una brecha real de fidelidad funcional que
vale la pena que el Arquitecto confirme si fue una simplificación consciente de Batch 2 o si el
checklist estructurado está planeado para un batch posterior. Si nunca se decidió explícitamente,
recomiendo tratarlo como deuda documentada, no bloquear por esto solo.

## Hallazgos NO reportados (fuera de alcance a propósito, confirmado en el brief y/o en el propio
código)

- Botón "Ver/Imprimir PDF" y "Cancelar ticket" del mockup — confirmado explícitamente como Batch 3
  (REQ-227/228) en `atlanticerp/CLAUDE.md`, no implementados a propósito.
- Tabla editable de "Productos reclamados/afectados" del mockup (con Marca/Referencia/Descripción/
  Cantidad) — confirmado en el brief de esta sesión como fuera de alcance ("no hay relación
  producto-ticket todavía"); la implementación muestra correctamente "No aplica para este tipo de
  ticket".
- "+ Agregar adjunto" del mockup en modo edición — mismo motivo, sin tabla de adjuntos todavía
  (comentario propio del backend lo confirma: "sin tabla de adjuntos de ticket todavía").
- Botón "Ver cotizaciones" — confirmado fuera de alcance en el brief de esta sesión.
- Diferencia cosmética: mockup muestra "Sin agendar" cuando no hay fecha; la app real muestra "—"
  (mismo significado, wording distinto — no lo cuento como hallazgo).
