### SCRUM-849 (sub-ítem 6/7 — foto ad-hoc) — 🟡 CRÍTICO encontrado y corregido en el mismo ciclo

**Camino feliz confirmado:** subir una foto válida a un ítem personalizado (`is_custom=true`)
muestra el botón con spinner (`Button loading`) mientras sube, y el thumbnail aparece después sin
recargar la página — el bug original de Daniela ("no muestra nada de ayuda visual") está resuelto.
El PDF de la cotización (`GET /quotes/{id}/pdf`) devuelve 200 con la foto ad-hoc incluida —
confirmado que `QuotePdfService::viewData()` no diverge de `QuoteController::formatDetail()`
(mismo payload), con test backend nuevo de esta sesión (`test_pdf_incluye_foto_ad_hoc_de_item_personalizado`,
ya en el diff antes de este Pre-QA) verde.

**CRÍTICO real encontrado — el camino de ruptura explícito que pide el ticket ("intentalo con un
archivo corrupto") seguía roto, de una forma peor que antes del fix:**

`QuoteItemController::uploadPhoto()` (línea ~475) solo capturaba `CircuitOpenException` (S3 caído)
alrededor de `QuoteItemPhotoService::uploadPhoto()`. Un archivo con extensión válida
(`extensions:` del `FormRequest` pasa) pero bytes que GD no puede decodificar (`imagecreatefromstring()`
devuelve `false`) lanza un `\RuntimeException` plano que **nunca se capturaba** — escapaba como
excepción no manejada, devolviendo **500** en vez de un 4xx.

- **Localmente (`APP_DEBUG=true`):** el 500 sí incluye el mensaje técnico crudo de la excepción
  ("GD no pudo decodificar la imagen subida") en el JSON, y el frontend (que sí tiene `onError` +
  fallback traducido desde el rebote anterior) lo muestra tal cual — visible, pero no traducido, y
  expone detalle de implementación interna (que se usa GD).
- **En producción (`APP_DEBUG=false`):** confirmado leyendo el handler default de Laravel
  (`convertExceptionToArray()`) — para cualquier excepción que no sea `HttpExceptionInterface`,
  el mensaje se reemplaza por el genérico **"Server Error"** en inglés. Como ese string SÍ llega
  en `response.data.message`, el frontend lo usa en vez de su propio fallback ya traducido
  ("No se pudo cargar la foto. Intentalo de nuevo.") — es decir, el fix de UX que este mismo
  ticket introdujo terminaba mostrando un mensaje **peor** que el fallback que ya tenían preparado,
  exactamente en el escenario de ruptura que Daniela pidió verificar.
- Confirmado en vivo con Playwright contra `localhost:5173` real (no solo lectura de código):
  request real `POST .../photo` con bytes inválidos → **500** antes del fix, cuerpo con el mensaje
  crudo de la excepción.

**Fix aplicado en el mismo ciclo** (regla dura de Pre-QA — no se documenta y se difiere):
`QuoteItemController::uploadPhoto()` ahora captura también `\RuntimeException` y devuelve **422**
con mensaje claro en español ("No se pudo procesar la imagen. Verificá que el archivo sea una
imagen válida (JPG, PNG o WEBP) y volvé a intentarlo."), mismo patrón que el resto de gates 422 de
ese controller. Test backend nuevo agregado (`QuoteItemControllerTest::test_subir_foto_con_bytes_invalidos_retorna_422_no_500`,
usa `UploadedFile::fake()->create()` para generar bytes no decodificables con extensión válida —
gap real de cobertura: ningún test existente ejercitaba este camino, todos usaban
`UploadedFile::fake()->image()` que siempre genera un GD válido).

**Re-check completo tras el fix (no solo el punto que falló):**
- `QuoteItemControllerTest` completo: **53/53** (antes 52, +1 test nuevo).
- `QuoteControllerTest` completo: **83/83** (incluye el test de PDF con foto ad-hoc).
- PHPStan Level 8 sobre el archivo tocado y full-project: **0 errores**.
- `--filter=VentasDiseno` (486 tests, todo el módulo, para agarrar cualquier regresión cruzada):
  **486/486**.
- Playwright en vivo, re-verificado contra `localhost:5173`: request real ahora devuelve **422**
  (nunca 500), error visible en la fila ("No se pudo procesar la imagen..."), spec permanente
  actualizado para congelar la regresión (ver abajo).
- Camino feliz (foto válida, spinner, thumbnail, PDF) re-confirmado sin cambios tras el fix.
