## Nota operativa — fricción de entorno, no hallazgo de producto

1. **Migración de tenant no se aplicaba vía `tenants:artisan migrate`/`--path`** en este Docker
   local (reportaba "Nothing to migrate" pese a la columna no existir) — se aplicó el `up()` de la
   migración directo vía tinker (`Schema::table` sobre el schema calificado). La suite automatizada
   (que sí corre esta misma migración con éxito vía `RefreshDatabase`) ya prueba que el archivo de
   migración en sí es correcto — esto es puramente un problema de invocación manual local, no del
   código del batch.
2. **Hallazgo real pero propio (no del producto):** al otorgar permisos de Compras a
   `designer@atlantic.test` vía tinker para poder probar SCRUM-830, un primer intento hizo
   `update(['extra_permissions' => json_encode([...])])` — doble-encodeo JSON (el cast `array` del
   modelo vuelve a hacer `json_encode` sobre un string), lo que dejaba `extra_permissions` como un
   string plano en vez de array y rompía el login con `TypeError: array_merge(): Argument #2 must
   be of type array, string given` en `User::plainEscapeHatchPermissions()`. Corregido pasando un
   array nativo. Documentado por transparencia — no es un bug de SCRUM-829/830/832, es un error de
   mis propios datos de prueba.
3. Un `designer@atlantic.test` con `compras.read/write/edit` en v1 pero sin
   `RoleModuleVisibility` v2 para el módulo `compras` queda redirigido a Inicio al navegar directo
   a `/inventario` — mismo gap v1/v2 ya diagnosticado y resuelto para Sustitutos en SCRUM-818, pero
   **no** para el resto de Compras. Fuera de alcance de este batch (SCRUM-830 no toca permisos),
   así que las pruebas de creación/edición de producto se corrieron con `superadmin@atlantic.test`
   en su lugar. **Señalado para que el Arquitecto decida si amerita un ticket de seguimiento**
   (mismo patrón que SCRUM-818, podría afectar a cualquier vendedor/diseñador real con
   `extra_permissions` de Compras otorgadas a mano sin el grant v2 correspondiente).
