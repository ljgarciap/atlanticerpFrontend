# Pre-QA — SCRUM-826 (2026-09-02)

Ban de CrowdSec en Logística para roles sin `compras.read` (Compras, épica SCRUM-328). Decisión de
negocio ya resuelta por Luis antes de implementar: bodega.read/compras.limited.view SÍ deberían
ver el checklist de documentos — se amplió el permiso en backend, sin tocar frontend.

## Corrido en LOCAL contra `http://localhost:8090`, no `dev.atlanticerp.ai`

Se sembró (vía tinker, después del último `infra/test.sh` de la sesión): 1 `Provider` + 12
`PurchaseOrder` en estado `ordenado` (entra en `active_shipments`, el filtro real de Logística), y
`extra_permissions: ["compras.limited.view"]` en `designer@atlantic.test` — el permiso
realmente alcanzable vía el gate de frontend de `/compras/logistica`
(`RequirePermission permission={["compras.read", "compras.limited.view"]}`, `bodega.read` no está
ahí, así que ese caso solo se verificó a nivel API vía PHPUnit, no es alcanzable por esta pantalla
en la práctica hoy).

## Verificación adversarial de que el test realmente detecta el bug (no falso positivo)

Antes de dar la pasada por buena, se revirtió el fix (`git stash`) y se corrió el mismo spec de
Playwright: **falló exactamente como predice el incidente real** — 12+ respuestas `403` distintas
en `GET .../documents` (una por orden visible, con reintentos de React Query incluidos), disparando
el mismo patrón que satura el bucket de `crowdsecurity/http-probing` (capacity=10). Se restauró el
fix (`git stash pop`) y se confirmó verde de nuevo. Este ciclo revertir→fallar→restaurar→pasar es
la evidencia de que el test no es vacuo.

## Escenarios de ruptura intentados

| Escenario | Resultado |
|---|---|
| `compras.limited.view` sin `compras.read`, 12 órdenes visibles en Logística | 0 respuestas 403 en `/documents`, todas 200 — el escenario real del incidente ya no se dispara |
| `compras.read` (regresión) | Sigue viendo la sección de documentos normalmente, sin cambios |
| `bodega.read` sin `compras.read` (vía API directa, PHPUnit) | 200 — el backend acepta el permiso aunque hoy no sea alcanzable por Logística en la UI |
| Rol sin ninguno de los 3 permisos (regresión) | Sigue en 403 — el gate no se abrió de más |
| `store()`/`validate()`/`validation()` del mismo controller | Sin tocar, siguen en `compras.edit`/`compras.read` — el fix se acotó exactamente a `index()` |

## Cobertura de tests (no solo el check en vivo)

Backend: 4 tests nuevos (`PurchaseOrderDocumentControllerTest`) + 3 ya existentes (sin regresión).
Suite completa 2982/2982, PHPStan Level 8 limpio en `app/Modules/Compras`.

Frontend: 2 tests E2E nuevos y permanentes
(`e2e/preqa-scrum826-logistica-crowdsec-20260902.spec.ts`), verificados en ambas direcciones
(fallan sin el fix, pasan con el fix) — promovidos según la regla del proyecto de no descartar
smoke tests de gates de permisos que ya causaron un incidente real.

## Hallazgos
