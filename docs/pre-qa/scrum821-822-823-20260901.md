## SCRUM-821 — Validar en API modalidad/etapa de fechas de entrega

Gap real: SCRUM-817 (Pre-QA 2026-08-31) había corregido el bloqueo en frontend y normalizado
`delivery_dates` server-side para el caso "single", pero la API seguía aceptando `partial` con
menos de 2 fechas, y fechas fuera de las etapas Propuesta/Aprobado, si se llamaba directo (curl,
otro cliente).

**Verificado en vivo contra dev.atlanticerp.ai:**
- `PUT /pipeline/187` (etapa `approved`) con `delivery_type=partial` + 1 fecha → `422`,
  `"La modalidad \"Parcial\" requiere al menos 2 fechas de entrega."` ✅
- `PUT /pipeline/158` (etapa `lead`) con `delivery_type=single` + 1 fecha → `422`,
  `"La fecha de entrega solo se puede definir en las etapas Propuesta o Aprobado."` ✅
- Regresión: actualizar OTRO campo en una tarjeta en `lead` (sin tocar `delivery_type`/
  `delivery_dates`) sigue permitido — cubierto por test automatizado, no reintroduce falso bloqueo.

Backend: 41/41 tests del módulo, suite completa 2906/2906.

## SCRUM-822 — Cargo, fecha de ingreso y jefe directo en usuarios

Gap real: REQ-548 original de "Registrar nuevo usuario" nunca implementó `job_title`, `hire_date`,
`manager_id` ni el estado configurable al crear (`is_active`, antes hardcodeado `true`).

**Verificado en vivo contra dev.atlanticerp.ai:**
- `POST /users` con `job_title`/`hire_date`/`manager_id: null`/`is_active: false` → 201, todos los
  campos persisten, `manager: null` (RN2 — "Ninguno — Socio Director"), sin envío de WelcomeMail. ✅
- `PUT /users/{id}` asignando `manager_id` a un usuario real → `manager: {id, name}` en la
  respuesta. ✅
- `PUT /users/{id}` con `manager_id` = su propio id (con `Accept: application/json`, igual que el
  cliente real vía axios) → `422`, `"Un usuario no puede ser su propio jefe directo."` ✅
  (Nota: sin ese header Laravel redirige 302 en vez de devolver JSON — comportamiento estándar de
  Laravel para requests que no piden JSON explícitamente, no es un bug; axios del frontend siempre
  manda `Accept: application/json`.)
- Playwright contra `dev.atlanticerp.ai/security/users`, login real, modal "Nuevo usuario": los 4 campos
  (Cargo, Fecha de ingreso, Jefe directo, Usuario activo) visibles y con el estilo de marca —
  screenshot verificado, ver captura de la sesión.

Backend: 9 tests nuevos + toda la suite de `UserControllerTest` (48/48), PHPStan limpio,
suite completa 2906/2906. Frontend: 15/15 en `UserFormDrawer.test.tsx`/`UserVisibilityModal.test.tsx`,
suite completa 1663/1663.

## SCRUM-823 — Revocación inmediata de sesión al desactivar/eliminar usuario

Gap real: un JWT ya emitido seguía siendo válido hasta su expiración natural aunque el usuario
fuera desactivado o eliminado — decisión de Luis (explícita, vía AskUserQuestion): revocación
inmediata sí es necesaria (riesgo real).

**Verificado en vivo contra dev.atlanticerp.ai** (usuario `electrician@atlantic.test`, id 50):
- Token válido antes de desactivar → `GET /users/catalog` → `200`.
- `PATCH /users/50/status` con `is_active: false` → `200`.
- MISMO token, mismo request → `401`. ✅ Revocación inmediata confirmada.
- Reactivado al final (`is_active: true` → `200`) — sin dejar el usuario de prueba inconsistente.

Backend: 6/6 tests de `JwtMiddlewareTest`, suite completa 2906/2906.
