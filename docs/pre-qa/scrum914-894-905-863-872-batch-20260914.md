## SCRUM-914 — Guía de Entrega mostraba "Estado: packing"

**Escenario de ruptura ejecutado:** pedido real PED-2026-0004 (id 4) en Packing, con 3 items. Se
registró una entrega PARCIAL real vía `RegisterDeliveryModal` (no vía API directa) — 2 items
completos, 1 en 0 unidades por falta de stock (motivo `sin_stock`) — y se verificó el documento
generado tanto en la vista previa en-app como en el PDF real descargado (URL presignada).

- Stage del pedido tras la entrega, vía API: `por_despachar` (nunca `packing`). ✓
- PDF real descargado y extraído con `pdftotext`: `Estado de la entrega: por_despachar`. ✓
- Confirmado también que el reorden (`transitionStage()` antes de `generateGuiaEntrega()`) no
  rompe la creación de la tarjeta "Faltante" para el item en 0 unidades — la familia del pedido
  pasó de 2 a 3 tarjetas correctamente tras el shortfall.

**Lo que sí funciona:** transición de etapa, generación de documento, tarjeta de faltante,
reasignación de reservas (`reallocateForProducts`).

## SCRUM-872 — CRÍTICO encontrado: el fix de backend no alcanza a la UI

El Arquitecto reportó esto como "ya resuelto por commits previos, solo falta el dato real" — Pre-QA
encontró que el criterio de aceptación real ("se puede vaciar un campo de texto ya cargado") **NO
se cumple de punta a punta** pese a que el backend sí lo permite.

**Causa raíz:** `UpdateFiscalSettingsRequest` (backend, fix SCRUM-857/858) tiene reglas
`['sometimes', 'string', 'max:N']` para `razon_social`/`nombre_comercial`/`ruc`/`dv`/
`direccion_fiscal` — sin `required` ni `min:1`, y hay un test de regresión backend real
(`test_update_permite_vaciar_un_campo_de_texto_ya_cargado`) que lo confirma. Pero el schema de
**Zod** de `FiscalConfigPage.tsx` (frontend) seguía con `z.string().min(1, ...)` en esos mismos 5
campos. `react-hook-form` + `zodResolver` bloquea el `handleSubmit` ANTES de llamar a la mutación
si la validación falla — el PUT real **nunca sale**.

**Reproducido en vivo contra dev.atlanticerp.ai** (login Aprobador, `gerencia3@test.com`, único con
acceso — password real confirmado: su propio email, no `B1n4X_2026?` que figura en memoria vieja):
1. Editar → vaciar "Nombre comercial" → "Guardar cambios" → aparece confirmación → "Confirmar".
2. El campo se marca en rojo con "Este campo es obligatorio." (screenshot
   `test-results/scrum872-fiscal-after-empty-save.png`).
3. **0 requests PUT `/fiscal-settings` disparados** — confirmado con listener de red en Playwright.
4. El dato en BD permanece sin cambios (verificado por API tras el intento: `nombre_comercial`
   sigue en `"ATLANTIC USA CORP"`, no se corrompió nada).

Este es exactamente el bug original que el ticket dice resolver — sigue intacto desde la UI, solo
que ahora la causa está en un lugar distinto (frontend, no backend). Es el mismo patrón de
mismatch frontend/backend ya señalado como recurrente en memoria
(`feedback_shape_mismatch_bugs_only_caught_by_preqa_gate`).

**Corregido en el ciclo (fix chico, no requirió reasignación a PM/Backend Dev):**
`atlanticerp-frontend` commit `d85d411` — `buildSchema()` en `FiscalConfigPage.tsx`: los 5 campos pasan
de `z.string().min(1, required)` a `z.string()`, alineado 1:1 con las reglas reales del backend.
Agregado test de regresión `permite vaciar un campo de texto ya cargado (nombre_comercial) y
dispara el PUT real, sin bloqueo de validación` en `FiscalConfigPage.test.tsx` — falla sin el fix
(bloqueado por Zod), pasa con el fix. Suite completa corrida antes de push: `npx vitest run` → 168
archivos, 1839 tests, todos verdes. Commit pusheado a `origin/dev`.

**Pendiente — bloquea el cierre de este batch (regla dura de Pre-QA, ver `pre-qa.md`):**
el deploy de este fix a `dev.atlanticerp.ai` quedó bloqueado por el clasificador de auto-modo de esta
sesión (`[Modify Shared Resources]` sobre `infra/deploy-manual.sh dev`, que hace `rsync` +

con el bug. **SCRUM-872 se queda en `Dev Testing`, no transiciona a `QA`**, hasta que:
